# Routine Bills & Subscriptions: first increment

Preserves Figure 4.24 RoutineBill's 13 exact attributes: billId, userId, expenseCategoryId, billName, billType, amount, dueDate, frequency, paymentMethod, reminderPeriod, description, status, createdDate. Additional recurrenceAnchorDay preserves the selected scheduled day across short months. User and ExpenseCategory are navigation properties. dueDate means the next unpaid scheduled occurrence; status starts Active. overdue/due-today/upcoming are display states calculated using the current Malaysia date, not persisted status changes.

Added RoutineBillPayment prepares the agreed history/expense linkage: paymentId, billId, expenseId, dueDate (scheduled), paidDate (actual), amount, paymentMethod, billNameSnapshot, createdDate. Unique billId/dueDate prevents duplicate payment of a scheduled occurrence; unique expenseId prevents attaching the same expense to multiple payments. All four foreign keys (two bill ownership/category, two history bill/expense) restrict deletion to preserve history. No payment rows are created in this increment.

Authenticated ordinary User accounts create/list only their own bills. Legacy Parent-role accounts remain compatible; Admin work is unchanged. Create binds a dedicated view model, derives owner from claims, and server-validates active account/category, accepted enum options, amount limits and cent precision, a MySQL-compatible date, description/name lengths and reminder days. Writes require POST + antiforgery and a transaction. Dates today and past unpaid dates are supported; past dates display Overdue.

Types: Bill/Subscription. Frequency: OneTime/Weekly/Monthly/Quarterly/Yearly. Payment methods match existing expense choices. Reminder period is an integer 0–365 days, with 0 meaning due-day. These selectable values and ranges are implementation choices. Creating a schedule does not add an expense, deduct money, run reminders, or change the next date automatically. The first increment implements model/schema, creation, owner-scoped list and sidebar route only. Edit/delete, filtering, Mark as paid with one linked expense per occurrence, recurrence advancement from scheduled date, reminders and dashboard integration remain subsequent increments.

Apply AddRoutineBills locally using Update-Database before visiting Routine Bills in the sidebar. Apply the matching Azure migration before any deployment. No application database was updated by Codex. Test create a bill and subscription, exact amounts, today/overdue dates, inactive/forged category and dropdown values, owner/role boundaries, rejected extra decimal precision, CSRF and mobile layout. Payment-history constraints are tested separately with synthetic expense records in a disposable database.


## Edit/delete increment
Owner-scoped Edit and Delete actions are available. They use the original fields and require no additional migration. Editing shares create validation, derives owner from claims, locks the account and preserves the ID/creation date. Active/Inactive is selectable; existing Completed status may be retained. A schedule cannot be made active for an occurrence already in payment history. Changing the due date or frequency resets recurrenceAnchorDay; unrelated edits preserve the original anchor across short months.

An edit stamp hashes persisted scalar state for stale-form detection without an additional database column. Edit/delete confirmations recheck it inside the account-locked transaction so a stale form cannot overwrite a later edit or payment advancement. POST mutations require antiforgery. Deleted bills are archived using status=Deleted and excluded from lists; no expense or payment history is deleted. Delete GET only confirms and makes no database changes. Active/Inactive counts and due-date display update after edits. Mark as paid, filtering, reminder dispatch and dashboard integration remain subsequent increments.

## Payment recording
- Mark as paid confirms an already-made full payment (actual amount/date/method), creates exactly one linked expense, and stores a payment snapshot in one transaction. It does not debit a bank account. Payment dates use Malaysia today and cannot be future-dated; early payments within the due month are allowed; future due months are blocked in the list, GET form, and POST service.
- Only active owned schedules can be paid. Stale confirmations and duplicate scheduled dates are rejected. Inactive categories must be replaced before paying.
- Weekly advances seven days; monthly/quarterly/yearly advance from the scheduled date, preserving the original day across short months. Overdue payments advance one occurrence at a time. One-time bills become Completed.
- History includes archived schedules and is paginated and owner-scoped. Transaction lists show View payment for linked expenses, opening the owner-scoped payment entry. Linked expenses are read-only in ExpenseController to preserve consistency with payment snapshots. They count in all existing expense totals on the actual payment date; do not add the same payment manually again.
- No additional schema migration beyond AddRoutineBills is required. Reminders and schedule filtering are separate steps.

## Payment history filters
Search bill snapshots or expense references; filter actual payment month and method. AJAX search waits 350ms, filters reset pagination, links retain filters, browser Back/Forward restores them. Reset clears even an exact expense selection. GET forms and pagination work without JavaScript. Invalid server filters return 400; failed AJAX requests retain previous results. Owner scope is applied before every filter. No migration required.
