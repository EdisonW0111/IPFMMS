# User-side monitoring requests

A user may have zero or many outgoing and incoming relationships, and may be monitored while also monitoring other people. Every relationship is directional and needs its own recipient acceptance. Ordinary User accounts stay unchanged. Admin implementation is deferred and untouched by this increment.

Figure 4.24 ParentStudentLink original attributes remain intact. Additions: requestedDate, acceptedDate, requestVersion, lastEmailAttemptDate, emailSentDate. A unique parentId/userId pair is reused with an incremented requestVersion after rejected/cancelled/disconnected requests. Stale forms cannot accept a replacement request. linkedDate becomes the acceptance date on acceptance; requestedDate records initiation. acceptedDate is cleared on disconnect and every new request. Legacy or Admin-created Active rows without acceptedDate do not pass CanMonitorAsync.

Parental Monitoring -> Send linking request -> email address. Eligible active users only; self requests and duplicate Pending/consented Active requests are rejected. The recipient alone can accept or reject while authenticated. Only the requester can cancel pending requests or resend mail. Either party can disconnect. Transitions lock both account rows in stable order under serializable transactions and recheck current status/version. Views and queries only expose the authenticated user's own relationships. All mutations use POST and antiforgery. Form data never selects the current identity. Request ownership is also checked in the service.

Email uses existing SmtpSettings through IParentLinkEmailSender/EmailService; no new SMTP credentials. The message tells the recipient to sign in to their usual IPFMMS website and open Parental Monitoring -> Requests received. There is no email click that grants access, no bearer token, and no new host URL configuration. Persist Pending before sending; if SMTP fails the request stays visible in-app and the sender sees a warning. Manual resend is available with a one-minute cooldown per relationship. Re-request also has a one-minute cooldown. No real email is sent by tests (fake mail sender only).

Apply AddParentLinkRequests locally before opening the new screens; it adds nullable consent/email metadata and a default-zero version to existing links, without rewriting their statuses or granting consent. The earlier AddParentStudentLink migration is still needed if not applied. Deploy schema to Azure before matching code. This increment implements requests and the shared authorization guard; financial summary monitoring and alerts remain subsequent increments.

Testing: two ordinary accounts A/B, A requests B, B sees incoming and explicitly accepts/rejects, A cannot self-accept, unrelated C gets no access; reciprocal B->A independent; A/B can have other links. Check duplicate/self/inactive requests, stale versions, cancellation, disconnect revocation, SMTP failure/resend, CSRF, pagination and mobile rendering.
