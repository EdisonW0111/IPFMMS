# Alert emails, AJAX filtering and relationship deletion

The five ParentStudentLink and eight Notification diagram attributes are unchanged. New schema: Notification.emailStatus (default NotRequested), emailAttemptedDate, emailSentDate; ParentStudentLink.parentHiddenDate, studentHiddenDate. Apply AddAlertEmailAndRelationshipDeletion locally and to Azure before matching code. No application database was updated by Codex.

New financial alerts queue email using existing SmtpSettings via IAlertEmailSender/EmailService. Existing alerts default NotRequested so deploying does not bulk-email old history; the user may choose Send email individually. At most three pending emails are attempted per alert refresh. A durable atomic Pending->Sending claim prevents multiple tabs/instances sending the same queued alert. Consent and current account eligibility are rechecked before delivery while holding the account locks shared with disconnect. Sent emails are not automatically resent. Failures remain in-app with a manual Retry email option after one minute. Existing alert event-key deduplication is unchanged. Delivery status is separate from read/unread state.

Detection still runs on app/page checks (and while a monitoring user's tab is visible), not an always-on scheduler. No emails are promised while the app is asleep. No new SMTP credentials or Azure setting is required. Tests inject fake mail senders and never email real users. SMTP transport cannot give an absolute exactly-once guarantee in an ambiguous connection failure. A process crash after claiming may leave Sending; do not automatically reset such claims, because an email might already have been accepted. Manual operational reconciliation is required for ambiguous sends.

Notifications filter and pagination GETs return a shared partial for X-Requested-With XMLHttpRequest. Filter changes, Reset, read/unread, mark-all and email retry work without full page reload, retaining filters. GET cancellation plus request sequencing suppress stale filter responses. Browser history/back is supported, errors retain previous results, and normal links/forms work without JavaScript. All mutations retain POST and antiforgery and owner/consent filtering.

Delete is available only for Inactive or Rejected links and only for a participant. GET is confirmation only; POST rechecks ownership, version and terminal status under account locks, then hides it only in that participant's list. The other participant's history, reverse-direction links, financial records and stored notifications are retained. This avoids deleting a shared relationship or breaking notification foreign keys. A later request reuses the pair with incremented requestVersion, clears both hidden markers, and requires fresh acceptance. Active and Pending relationships must be disconnected/rejected first; Cancelled deletion is outside the requested scope. Admin functionality unchanged.
